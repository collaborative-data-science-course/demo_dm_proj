# Git Branches – Purpose, Usage & Best Practices

---

## Why Branches Matter

In collaborative projects, **everyone works on different tasks at the same time**: features, bug fixes, documentation, experiments, etc.  
But if everyone worked directly on the `main` branch — chaos would follow!

Branches allow:

- Safe experimentation without affecting others
- Isolated development of features, fixes, or documentation
- Cleaner integration with **Pull Requests**

> Think of branches as "parallel universes" of your codebase. You can try anything without breaking production.

---

## What Is a Git Branch?

A **branch** is a lightweight movable pointer to a commit.

- `main` or `master`: The stable production-ready branch
- `feature/xyz`: A new feature you're building
- `fix/bug-404`: A specific bug fix
- `experiment/new-model`: Trying out something new

---

## Basic Branch Commands

### View Current Branch

```bash
git branch
```

### Create a New Branch

```bash
git branch feature/my-new-feature
```

### Switch to That Branch

```bash
git checkout feature/my-new-feature
```

Or in one step:

```bash
git checkout -b feature/my-new-feature 
#creates a new branch `feature/my-new-feature ` and switches to it
```

### Make Changes and Commit on Your New Branch

```bash
git add .
git commit -m "Add feature logic to new branch"
```

---

Now, to push and update the work from your branch to the `main` branch there are 2 options:

### Option-1: Merge Changes Into Main (Not Recommended in a Team setting)

    1. Switch to the `main` branch:

    ```bash
    git checkout main
    ```

    2. Merge the feature:

    ```bash
    git merge feature/my-new-feature
    ```

    3. Push the merged result:

    ```bash
    git push origin main
    ```
    ---

### Optional: Delete the Feature Branch

Once merged:

```bash
git branch -d feature/my-new-feature

```

---

### Option-2: Using GitHub for Merge (Pull Requests)

Best practice for teams:
- Push your branch to GitHub

```bash
git push origin feature/my-new-feature
```

- Go to GitHub repo
- Click "Compare & Pull Request"
- Assign reviewer(s)
- Review, comment, and merge into main
- GitHub handles the merge safely

## Common Branching Strategies

### 1. Main + Feature Branches (Simple)

```
main
 └─ feature/add-plot
 └─ fix/missing-data

```
Best for small teams and short-term projects

### 2.  Main + Dev + Feature Branches (Staged)

```
main → production-ready
dev → latest approved features
 └─ feature/abc
 └─ feature/xyz

```
- Team merges features into `dev`
- After QA/review, `dev` gets merged into `main`

### 3.  Git Flow (Advanced)

```
main
develop
 └─ feature/
 └─ release/
 └─ hotfix/

```
Popular in enterprise projects — but overkill for beginners

## Branch Naming Conventions

Stick to meaningful and structured names:

| Type       | Format Example             |
| ---------- | -------------------------- |
| Feature    | `feature/login-page`       |
| Bug Fix    | `fix/crash-on-empty-input` |
| Docs       | `docs/readme-update`       |
| Experiment | `experiment/alt-model`     |


Use hyphens - or slashes / to improve readability.

---

## Why Not Just Use Main?

- Mistakes go live immediately
- Everyone's changes conflict
- Hard to test isolated work
- Pull requests become complicated

Branches provide focus, safety, and clarity.

---

## Summary
- Branches allow isolated development
- Use checkout -b to create and switch to a new branch
- Push branches to GitHub for PR reviews
- Follow clear naming conventions
- Merge carefully and delete old branches after use
